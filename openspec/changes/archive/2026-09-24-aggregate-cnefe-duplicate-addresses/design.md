## Context

See `proposal.md` for motivation. The project already has a CNEFE preparation script that writes municipality-partitioned FlatGeoBuf part files under `public/geodata/cnefe/` and a `manifest.json` that lists generated parts. The requested aggregation is a derived data-preparation step, not a UI change, and should not modify the raw converted CNEFE outputs.

## Goals / Non-Goals

**Goals:**
- Add a standalone maintainer-run aggregation script for CNEFE FlatGeoBuf inputs.
- Collapse only truly identical records: same point coordinates and same existing properties.
- Add `QUANTIDADE` to aggregated features with the number of collapsed records.
- Allow lightweight validation against one explicit FlatGeoBuf input file.
- Allow full-folder aggregation against a CNEFE output directory while processing files sequentially.
- Keep aggregated outputs separate from `public/geodata/cnefe/`.

**Non-Goals:**
- Re-run raw ZIP/CSV conversion.
- Change the existing CNEFE conversion script output format.
- Add frontend consumption of aggregated CNEFE assets.
- Infer near-duplicates, normalize addresses beyond existing properties, or spatially cluster points.

## Decisions

- Implement aggregation as a separate script instead of extending `prepare-cnefe-geodata.mjs`.
  - Rationale: conversion and aggregation are different maintainer workflows; keeping them separate allows validating one generated file without rerunning ZIP processing.
  - Alternative considered: add an aggregation flag to the conversion script. That would couple the workflows and make targeted aggregation less direct.

- Use generated FlatGeoBuf files as input.
  - Rationale: the existing conversion script already handles raw CNEFE ZIP parsing, property transformation, code decoding, geometry creation, and partitioning. Aggregating the converted assets avoids duplicating that logic.
  - Alternative considered: aggregate raw CSV rows. That would require repeating conversion rules and could diverge from the FlatGeoBuf assets used elsewhere.

- Write aggregated outputs under `public/geodata/cnefe-aggregated/`.
  - Rationale: the unaggregated CNEFE assets remain available for auditing and future workflows, while aggregated assets can be regenerated independently.
  - Alternative considered: overwrite `public/geodata/cnefe/`. That risks losing the original per-record data.

- Build the grouping key from geometry coordinates plus all existing feature properties except `QUANTIDADE`.
  - Rationale: the user requested grouping by all columns/information being equal. Excluding `QUANTIDADE` prevents rerunning aggregation over already aggregated output from fragmenting groups by previous counts.
  - Alternative considered: group only by address fields or decoded type fields. That would collapse records that differ in other retained properties, which contradicts the requested all-columns equality.

- Sort property keys when creating grouping keys.
  - Rationale: deterministic keys avoid false differences caused by JavaScript object property insertion order.
  - Alternative considered: stringify properties as-is. That is simpler but can be unstable if feature property order differs between inputs.

- Validate with one explicit FlatGeoBuf file, preferably one part generated by the CNEFE conversion script.
  - Rationale: the user explicitly asked to test with one file only, and full CNEFE aggregation can be expensive.
  - Alternative considered: aggregate the full manifest during initial validation. That is unnecessary for the requested proof and could be slow.

- Accept either one `.fgb` file path or one directory path as the CLI input.
  - Rationale: maintainers need both a lightweight single-file validation path and a practical command for aggregating the whole generated CNEFE folder.
  - Alternative considered: add separate commands for file and directory modes. That would be more explicit but adds unnecessary package-script surface for the same operation.

- For directory input, discover direct child `.fgb` files, sort them by file name, and process them sequentially.
  - Rationale: deterministic order makes logs reproducible, and sequential processing avoids retaining data from multiple FlatGeoBuf files in memory at once.
  - Alternative considered: process files in parallel. That could be faster but risks high memory usage with large CNEFE files.

- Mirror each input file name in the aggregated output directory.
  - Rationale: `public/geodata/cnefe/foo.fgb` should become `public/geodata/cnefe-aggregated/foo.fgb`, making source/output correspondence obvious.
  - Alternative considered: combine all aggregated outputs into one file. That would be harder to trace back to generated parts and may recreate memory pressure.

## Risks / Trade-offs

- FlatGeoBuf input reading may materialize all features from the chosen file -> acceptable for one-file validation, but full-manifest aggregation may need batching if files become very large.
- Directory mode may include many files -> process sequentially and log per-file progress so a failed file can be identified and rerun.
- Output file names must not collide with raw files -> write to a separate directory and mirror input base names.
- If maintainers accidentally pass an already aggregated input, `QUANTIDADE` should not participate in grouping -> explicitly ignore existing `QUANTIDADE` in the grouping key and recompute it.
- Exact-coordinate equality may miss records that are semantically the same but differ by tiny coordinate precision -> this is intentional because the requested grouping requires all information to be equal.

## Migration Plan

1. Add the standalone aggregation script under `scripts/`.
2. Add a package command for running aggregation.
3. Implement single-file FlatGeoBuf input aggregation and write output under `public/geodata/cnefe-aggregated/`.
4. Add directory input support that discovers `.fgb` files and processes them sequentially into the aggregated output directory.
5. Run the script against one generated CNEFE FlatGeoBuf file and verify `QUANTIDADE` exists in output features.
6. Run the script against the CNEFE output directory or a small directory fixture and verify one output is produced per input file.
7. Run syntax/build/OpenSpec validation.
